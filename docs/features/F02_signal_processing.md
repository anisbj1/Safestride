# F02 — Signal processing (IMU and PPG)

> Track **A** · Milestone **M1** · Runs on **firmware** · Contract changes only via change request.

## 1. Responsibility
Turn raw samples into `MotionFeatures` and `PpgFeatures` at 1 Hz: motion magnitude/intensity, orientation, dominant frequency, stillness duration; PPG filtering, beat detection, heart-rate, signal quality. Independent of any ML model.

## 3. Inputs and outputs

- `ImuSample`, `PpgSample` — one sample per message, read from the two F02 input
  queues in `AppContext` (`SpscQueue<ImuSample, N>`, `SpscQueue<PpgSample, N>`, D10):
  producer = F01 `SensorTask`, consumer = F02 `ProcessingTask`, N ≥

  integrator-owned `app.h` (features never edit it — wiring README); overflow is
  counted and reported per CR-004 and never blocks the producer.

**Outputs (produced contracts)**
- `MotionFeatures` (1 Hz, `LatestValue`)
- `PpgFeatures` (1 Hz, `LatestValue`)
- Optional debug: filtered PPG samples for F28 (research mode only)

## 6. Design decisions (problem → alternatives → trade-offs → choice)

**D1. Motion metric**
- Simplest: Raw acceleration magnitude mean.
- Professional/scalable: ENMO (max(|a|−1 g,0)), std, jerk, gyro RMS, dominant frequency.
- Trade-offs: ENMO is a standard actigraphy metric (comparable to literature) but assumes reasonably calibrated 1 g; drift matters little at arm-activity levels.
- **Choice:** ENMO + std + jerk + gyro RMS + tilt; dominant frequency via autocorrelation (cheaper than FFT for one band). Gravity via low-pass.

**D2. PPG heart rate**
- Simplest: Peak count over 10 s on lightly filtered IR.
- Professional/scalable: Band-pass, rhythm-constrained peak detection (PI noise floor + refractory lockout + tallest-in-window candidate; **FIX loop 4**: no amplitude-adaptive detection state — the old `0.5 × amp_ema_` term was a ratchet under real beat-to-beat jitter, rounds 3 and 7), median inter-beat interval, SQI from perfusion index and IBI plausibility, motion flag from IMU.
- Trade-offs: Scalable is more code but the MAX30102 signal is weak and motion-sensitive; a naive counter will produce confident wrong HR.
- **Choice:** Second option, implemented stepwise: (1) DC removal + biquad band-pass, (2) peak detection, (3) SQI gate (carried as `quality` + `hr_confidence`), (4) motion flag. Validity = beat-train plausibility only (D6, amended 2026-10-15): a failed *quality* gate no longer forces `hr_valid=false` — it surfaces as `quality` ≠ Good and low `hr_confidence`; only a failed *beat-plausibility* gate produces `hr_valid=false` ("--"). (F12 renders the plain `HR ###` for any fresh plausible rhythm — the uncertain `HR ~###?` marker was added and removed the same day, status log 2026-10-15; honesty about doubt lives in `quality`/`hr_confidence`.)

**D3. Filter type**
- Simplest: Moving-average.
- Professional/scalable: IIR biquad (Butterworth) with coefficients derived offline, documented with the design script.
- Trade-offs: IIR has phase distortion and needs stable fixed-point/float care; moving average blurs pulse peaks.
- **Choice:** Biquad band-pass 0.5–4 Hz `[DERIVED]` (30–240 bpm), coefficients generated by a documented script committed under `bw_signal/tools/`.

**D4. Windowing and sample staging (define/design session 2026-10-01)**
- Problem: the 1 s window boundary must be applied to two streams with independent, jittery timestamps, and both `MotionFeatures` and `PpgFeatures` for the *same* frame must be finalized together (`motion_corrupted` needs the IMU metrics of that frame). A sample with `t ≥ window_end` must not leak into the closing frame.
- Simplest: `feed()` writes straight into per-frame accumulators, routing by timestamp into current/next.
- Scalable: per-stream staging `RingBuffer` (timestamp-ordered) + one `FeatureWindowScheduler`; `step(now)` closes a frame only when a sample crossed the boundary or the stream stalled (`window_end + kMaxSampleGapMs`), draining staging into the frame accumulators in timestamp order. `step()` closes ≤ 1 window per call; the caller loops (`while (step(...))`) to catch up after a delayed task.
- Trade-offs: direct routing breaks when two closes are pending at once (samples beyond the *second* boundary land in the wrong bucket); staging costs RAM (IMU 128 × 32 B + PPG 256 × 24 B ≈ 10 KB) but makes ordering trivially correct and absorbs up to 2.56 s of task lateness before dropping (Overflow → window degrades, never crashes).
- **Choice:** staging + scheduler. Window boundaries are timestamp-driven; `IClock` is only read by the caller and passed in as `now_ms` (spec §3), keeping `SignalProcessor` pure and host-testable.

**D5. Motion state across windows (stillness, gravity, dominant frequency)**
- Simplest: compute everything inside one window, forget between windows.
- Scalable: stillness is a *continuous* duration → state machine persists across windows with hysteresis (enter `kStillnessEnmoThresholdG`, exit `kStillnessExitEnmoThresholdG`); gravity is a low-pass state (`kGravityTimeConstantMs`); dominant frequency uses a 4 s magnitude history (`kDominantFreqWindowMs`, autocorrelation, no FFT).
- Trade-offs: persistent state must be *reset* when data continuity breaks, otherwise a dead sensor reports ever-growing "stillness" (would mislead sleep inference) or a stale gravity/posture. 
- **Choice:** persistent state; any gap > `kMaxSampleGapMs` or an `Insufficient` window resets stillness to 0 and clears the magnitude history (gap breaks continuity by definition). Gravity is *kept* across gaps (it is an orientation prior that re-converges in ~2 time constants). Dominant frequency is computed from the *magnitude* signal (actigraphy convention — step-rate-like), reported as 0 until the 4 s history is full or when the autocorrelation peak < `kMinAutocorrPeakStrength` ("0 if none" per contract).

**D6. PPG quality composition and validity gates**
- Simplest: one ratio threshold (perfusion only) → `hr_valid`.
- Scalable: `sqi = π_factor × timing_factor × saturation_factor`, each factor 0..1 with a stated derivation; `DataQuality` is the worst rule that fires: 0 samples / coverage < `kMinWindowCoverageFrac` / saturation ≥ `kMaxSaturatedFraction` / `sqi < kMinSqiForValidHr` → `Insufficient`; gap > `kMaxSampleGapMs` or `motion_corrupted` → `Degraded`; else `Good`. `hr_valid = beats ≥ kMinBeatsForHr && median IBI ∈ [kPpgRefractoryMs, kIbiPlausibleMaxMs] && miss-tolerant consistency ≥ kMinIbiConsistencyFraction` (the 2×-band fraction, `kIbiMissedBeatMultiple` — FIX loop 4 — measured over the newest `kHrRecentIbiCount` IBIs, FIX loop 5; the strict 1× fraction over the whole lookback keeps feeding SQI and `hr_confidence`) — the estimator's plausibility triple ONLY, decoupled from `quality` on 2026-10-15 (see status log; no contract doc pinned the old coupling. Quality rides along untouched and `hr_confidence = sqi × consistency` still reports it honestly). **Verdict lifetime (FIX loop 5, state in `SignalProcessor` — the estimator stays a pure function):** once fresh-valid, consecutive fresh-invalid windows shorter than `kHrValidDropoutMs` HOLD the number (bpm keeps updating from the median) instead of flickering to `--`; a beat gap — newest accepted beat older than `kIbiPlausibleMaxMs` — clears validity and the hold immediately with precedence, so a finger-lift ghosts ≤ 2.5 s + one window. The plausibility rules themselves are never relaxed by either rule.
- Trade-offs: products are harsh (any weak factor drags sqi down) but explainable and weight-free; a weighted sum needs tunable weights with no data to tune them against yet.
- **Choice:** product of factors; median-IBI HR (robust to missed/extra beats); `hr_confidence = sqi × consistency`. Noise-only and saturated fixtures fail the perfusion/saturation factor → `Insufficient`, matching §9. `motion_corrupted` looks back over the whole HR window (`kHrWindowMs / kMotionWindowMs` frames), because an artifact corrupts beats for seconds, not just the frame it lands in; absent IMU data leaves the flag `false` (absence ≠ motion) so PPG-only operation still works.

**D7. Filter realization (resolves §13 open question: fixed point?)**
- Simplest: float moving-average; scalable: float32 Butterworth biquads (DF1), fixed-point only if CPU demands.
- **Choice:** float32 Direct-Form I, three sections (DC blocker HP 0.05 Hz, HP 0.5 Hz, LP 4.0 Hz, each Butterworth Q = 1/√2). DF1 chosen because steady-state initialization for the first sample is exact (`x1 = x2 = x0`, `y1 = y2 = H(1)·x0`), killing the ~3 s DC-blocker startup transient that would otherwise fake peaks. Precision: worst-case terms 50 000 counts × float eps ≈ 0.003 counts vs a 0.1 %-PI pulse ≥ 50 counts → 4 orders of magnitude margin. CPU: 3 sections × 100 Hz ≈ negligible. **Fixed point rejected** — measure CPU first (§14); no evidence it is needed.

**D8. RMSSD / HRV (deferred in v1)**
- Simplest: `hrv_valid = false` always; scalable: clean IBIs → RMSSD when quality allows.
- Trade-offs: RMSSD is 5 lines but needs IBI-cleaning to be meaningful, and no data exists yet to validate it (F28).
- **Choice:** defer — v1 emits `hrv_valid = false` (permitted by §12). Revisit at F29 with recorded captures.

**D9. Configuration style**
- Simplest: `constexpr` named constants (zero runtime cost); scalable: `SignalConfig` struct injected by the composition root and backed by F18 settings (`[USER]`).
- Trade-offs: a Config struct is dead plumbing today — no runtime settings exist yet (F18 not implemented) and no tuning data exists to expose.
- **Choice:** `constexpr` constants in `bw/signal/signal_config.h`, every one tagged and mirrored in §8, for now. When F18 lands, promote the `EXPERIMENTAL` ones into a `SignalConfig` + settings keys (change request if a contract type is needed).

**D10. F01→F02 input mailbox (defined 2026-10-02 — unblocks F01 D15)**
- Problem: F01's D15 defers `SensorTask` until "F02's input contract (mailbox/queue in `AppContext`)" exists. runtime.md §3.1 mandates the primitive (`SpscQueue` for ordered raw samples — `LatestValue` would silently drop timestamped samples) but the element shape and capacity are written nowhere, and `app.h` is integrator-owned (features never edit it), so F02 must at least *specify* the fields before anyone can add them.
- Element alternatives: **single sample** — simplest: reuses bw_core `ImuSample`/`PpgSample`, no new contract type, no CR, no partial-batch state; ~150 queue ops/s is trivial for a lock-free SPSC. **Batch per SensorTask drain** — scalable side: matches runtime.md's "raw sample batches" wording literally, fewer queue ops; but needs a batch type (bw_core change request or an app.h-local array+count), couples F01's drain size to F02, and adds partial-batch edge cases.
- Capacity alternatives: **< one consumer period** — cheapest, but the consumer runs at 1 s, so a queue holding less than one period overflows every single cycle. **One period + margin** (64 IMU ≈ 1.28 s, 128 PPG ≈ 1.28 s, ≈5 KB total) — survives a full late period plus 28 % jitter; overflow beyond that is counted per CR-004 and the window degrades (§10), never crashes. **2.56 s parity with D4 staging** — ~10 KB for lateness the internal staging already absorbs on the consumer side.
- **Choice (developer-confirmed 2026-10-02):** single-sample messages; the integrator adds `SpscQueue<bw::ImuSample, N>` + `SpscQueue<bw::PpgSample, N>` to `AppContext` with N ≥ the §8 minimums; producer = F01 `SensorTask`, consumer = F02 `ProcessingTask`; a failed `push` is counted/reported per CR-004 and never blocks the sensor task. Simplest = single sample + smallest correct queue; most scalable = batches + big queues — rejected as unnecessary at 150 msg/s with D4's staging behind the queue.

**D11. `bw_signal/library.json` (added 2026-10-03)**
- Problem: the 2026-10-01 status entry claimed a `library.json` shipped with the library; the file did not exist. Nothing was broken (`bw_core` also has none and PlatformIO resolves `lib/` folders fine), but the log was false and the lib declares no platform scope.
- Simplest: correct the status log only — zero files.
- Most scalable: a manifest, matching the sibling `bw_hal` precedent — declares `espressif32` + `native` scope and is the natural home for future dependencies.
- Trade-offs: the manifest is inert metadata today; the log-only fix leaves no place to declare a future dependency and keeps the divergence between the two "sources of truth" (log vs. tree).
- **Choice:** add the ~10-line manifest (no dependencies); tree and log now agree.

| Name | Value | Tag | Why |
|---|---|---|---|
| `kStandardGravityG` | 1.0 | `HW` | MPU6050 outputs are multiples of local g (datasheet: sensitivity configured in g/LSB) |
| `kImuSamplePeriodMs` | 20 | `DERIVED` | 50 Hz (01 §3.3: Nyquist margin for <20 Hz arm-motion energy) |

| `kStillnessExitEnmoThresholdG` | 0.05 | `EXPERIMENTAL` | Hysteresis exit = 2.5× enter so sensor noise at 0.02 cannot flap the state |
| `kGravityTimeConstantMs` | 2000 | `EXPERIMENTAL` | Slow enough that arm swing stays out of the gravity vector, fast enough to track posture change in ~2 s |
| `kDominantFreqWindowMs` | 4000 | `DERIVED` | 1/4 s ⇒ 0.25 Hz resolution (separates walking cadence bands); 200 samples × ≤98 lags ≈ 20 k MACs once per second |

| `kAutocorrTieMargin` | 0.02 | `EXPERIMENTAL` | Relative margin a longer lag must beat the best by; periodic signals tie at lag T, 2T… and the tie winner would report a subharmonic (1.5 Hz read as 0.75 Hz). 2 % ≫ float noise on ~50 samples, ≪ the ~40 % peak-to-neighbor gap |

| `kImuInputQueueMinCapacity` | 64 | `DERIVED` | AppContext input queue (D10) must hold one full 1 s consumer period (50 samples @50 Hz) + 28 % jitter; ≈2 KB; actual N spelled in integrator-owned `app.h` |
| `kPpgInputQueueMinCapacity` | 128 | `DERIVED` | Same rule at 100 Hz (100 samples/period + margin); ≈3 KB (D10) |
| `kPpgFilteredDebugCapacity` | 500 | `DERIVED` | 5 s of filtered IR for the F28 debug tap; larger replays use F28's raw capture path |
| `kMaxBeatsInHrWindow` | 40 | `DERIVED` | 10 s × 200 bpm = 33 beats + headroom (overflow overwrites oldest — history, not data loss) |
| `kMinBeatsForHr` | 4 | `DERIVED` | 10 s at the 0.5 Hz (30 bpm) band edge gives 5 beats; 4 tolerates one rejected artifact beat |
| `kPpgDcEmaAlpha` | 0.01 | `DERIVED` | τ = 1/(α·fs) ≈ 1 s at 100 Hz: slower than any beat (≥300 ms) so the noise floor does not chase the pulse |
| `kIbiPlausibleMaxMs` | 2500 | `DERIVED` | 30 bpm = 2000 ms is the band edge; longer than 2500 ms means a dropout, not a beat pair (min = `kPpgRefractoryMs`) |
| `kIbiMedianToleranceFrac` | 0.2 | `EXPERIMENTAL` | Sinus arrhythmia ≈10 %; missed/extra beats deviate ≥50 % — 20 % separates them |
| `kMinIbiConsistencyFraction` | 0.6 | `EXPERIMENTAL` | Below ~60 % consistent IBIs the timing is erratic → HR more likely wrong than right |
| `kIbiMissedBeatMultiple` | 2.0 | `DERIVED` | **FIX loop 4 (bench round 7):** an IBI of ~2× the median is ONE missed beat (pulse dipped below the detection floor), not arrhythmia — it now counts toward `kMinIbiConsistencyFraction` alongside 1× IBIs; a 3×+ gap stays a rhythm break. Self-limiting: the raw median is unchanged, so ≥ ~50 % misses skew it into no band and the train honestly fails. The strict 1× fraction still feeds SQI/`hr_confidence` (every miss stays a quality ding) |
| `kHrRecentIbiCount` | 4 | `DERIVED` | **FIX loop 5 (bench round 7):** validity-gate consistency horizon — `consistency_miss_tolerant` counts the NEWEST 4 IBIs, not the whole `kHrWindowMs` lookback, so a weak-perfusion/micro-motion stretch ages out of the gate within ~2 windows of its end instead of holding `hr_valid=false` for the rest of the 10 s (round 7: a ~4 s weak stretch produced 14 s `--` flickers under steady contact). Why 4: it is `kMinBeatsForHr` expressed in IBIs (the floor for how many IBIs exist at the first possible verdict, so latency never grows), ≈3.4 s at 70 bpm; one artifact IBI among 4 still passes (3/4 = 0.75 ≥ `kMinIbiConsistencyFraction`), two consecutive bad fail (0.5). Median and strict `consistency` (SQI/`hr_confidence`) stay full-window — reliability of the whole window is exactly what those must keep honest |
| `kHrValidDropoutMs` | 5000 | `DERIVED` | **FIX loop 5:** `hr_valid` hold timeout — once a window was plausibly valid, consecutive fresh-invalid windows shorter than this KEEP the number (bpm updates from the median) instead of flickering to `--`; upper edge of the developer's 3–5 s band: long enough to ride a 4 s weak stretch plus the ~1 window its bad IBIs need to age out of `kHrRecentIbiCount`, short enough that a genuine rhythm change shows within ~5 s. Never outlives a beat gap (newest accepted beat older than `kIbiPlausibleMaxMs` clears immediately): a finger-lift ghosts ≤ 2.5 s + one window regardless of this timeout |
| `kMaxSaturatedFraction` | 0.02 | `EXPERIMENTAL` | A couple of clipped samples per window are ADC glitches; ≥2 % means the pulse left the linear range |
| `kSqiFullPerfusionRef` | 0.004 | `EXPERIMENTAL` | Full-quality perfusion reference **recalibrated 2026-10-14 against the first real-sensor data** (tester ground truth: working pulse = AC 500–2000 counts on DC ~150 000 → PI band ≈ 0.3–1.3 %; 0.4 % = rms-PI of a weak-but-clear pulse ≈ peak 600 counts @ DC 163 000). The previous 1 % demanded ≈ 4600 counts p-p — a level the bench never produced — and capped sqi at 0.18 for a pulse the tester reads comfortably (H3, loop-2b audit) |
| `kMinSqiForValidHr` | 0.4 | `EXPERIMENTAL` | Composition below ~0.4 means one factor weak or two mediocre |
| `kMinWindowCoverageFrac` | 0.5 | `EXPERIMENTAL` | Half a window of real samples is the least from which mean/std are meaningful |

All values are starting points unless tagged `[HW]`; tune with data (F28/F29).

## 9. Test plan
- Synthetic sinusoid PPG at 50/70/120 bpm → HR within ±3 bpm `[EXPERIMENTAL]`.
- Noise-only (no perfusion, peaks below the floor → zero beats) → `hr_valid=false`, quality `Insufficient`. Noise ABOVE the 0.1 % floor → never quality `Good`, never confidence ≥ `kMinSqiForValidHr` (2026-10-15 re-scope: a random train can pass the plausibility triple and show as a plain `HR ###` — same accepted class as a motion false-HR, doubt carried by `quality`/`hr_confidence`). Saturated-flag input → quality `Insufficient` (the fixture's regular train still reads `hr_valid=true`; the flag is a quality input, and real clipping jitters timing so the consistency gate rejects mangled trains). Low-perfusion but regular train (DC 163 000, AC 300) → `hr_valid=true`, quality `Insufficient`, confidence < `kMinSqiForValidHr`.
- ±50 % beat-to-beat amplitude jitter (DC 160 000, 70 bpm, 60 s) → `hr_valid=true` in ≥95 % of windows (FIX loop 4; before: 34/60 = 57 % with the adaptive-threshold ratchet), median bpm ±3, no starvation episodes.
- **hr_valid lifetime (FIX loop 5):** (a) jitter train + 4 s weak-perfusion dip (amp 600 ≈ PI 0.0027 + ±800-count deterministic band noise) → `hr_valid` stays true through every dip AND recovery window with bpm 70 ± 3; before: `--` at dip+5–6 s as the poisoned stretch matured in the full-window gate (the round-7 pattern). (b) valid 12 s → silence → first invalid within `kIbiPlausibleMaxMs` + one window of the last data window (after: 2000 ms; before: 7000 ms — the 10 s beat-lookback ghost). (c) noisy contact onset + clean train → first display ≤ 8 s and stays valid (measured 7000 ms; bench round 7 before-fix: 14 s; a full-window-Median-capped harsh-onset probe measured 9000 ms — the median age-out this loop deliberately does not touch, see status log). (d) sustained 5000/1500 ms pulse alternation with beats present (`ppg_beat_count ≥ kMinBeatsForHr`) → every window past hold expiry reads invalid: the hold never rescues arrhythmia, and the gap rule is structurally silent there (max spacing < `kIbiPlausibleMaxMs`) so only hold expiry can clear.
- Missed-beat tolerance vs arrhythmia (estimator level): 45 % doubled IBIs (6×600 ms + 5×1200 ms) → valid via the 2× band with the correct 600 ms median; IBIs alternating 500/1500 ms → invalid (arrhythmia is never smoothed into a clean number).
- Motion-corrupted window flagged when IMU energy high.
- IMU: constant 1 g gives ENMO 0; known step signal gives expected stillness_ms; tilt for the 6 axis orientations.
- Timestamp gaps/wrap; first-window startup behavior; recorded fixtures replayed via F28 (optional — only if recordings ever exist; prototype scope, 2026-10-02).

## 10. Failure behavior
- No new samples ⇒ features carry `quality=Insufficient` and stale-marked timestamps; never repeat the last HR as valid.
- Sample gap → window marked Degraded.
- Never crash on missing/invalid input; return `Err` or an output flagged `Insufficient`.

## 11. Budget
